# LifeAgent 日历、日程提醒与演示数据设计

## 目标

解决三个实际测试问题：

1. 页面打开或刷新时不应自动写入默认演示数据；
2. 日历可以浏览今天之后的日期；
3. 用户输入带有相对日期、时间和提前提醒的日程时，后端保存日程与提醒，前端在对应未来日期显示。

## 非目标

- 本轮不实现操作系统推送、邮件或企业微信通知；
- 不重写已验证的 Agent 核心流程；
- 不改变现有聊天 API 的必填字段；
- 不清理真实用户数据，只处理明确标记的演示数据。

## 现状与根因

- `Timeline.tsx` 只生成过去 7 天的日期，并向后端请求最近数据，因此今天之后没有可选日期。
- 页面加载使用只读的 `GET /api/v1/life-events`，仓库内没有前端自动 seed 调用；重复数据来自固定演示用户或之前执行的 seed 脚本。需要把 seed 明确变为显式、幂等操作。
- `life_events.event_time` 目前对“明天下午三点”等中文相对时间无法标准化，SQL 层会保存为 `NULL`，导致未来日程无法按日期显示。

## 设计

### 1. 演示数据生命周期

- 页面加载、刷新和普通 API 查询均保持只读。
- `seed_simulation_data.py` 增加幂等策略：使用固定的演示用户与标记 conversation，重复执行前先删除同一标记范围的记录，或在唯一键约束下跳过重复项；不执行全表清空。
- 如果未来需要网页端演示数据，增加显式“加载示例数据”操作，默认关闭，不在 `useEffect` 或页面初始化中触发。
- 增加测试：连续执行页面查询两次，数据库写入次数为零；重复执行 seed 不增加同一演示批次的记录。

### 2. 日期范围与查询

- 前端日期范围默认为过去 7 天、今天和未来 30 天。
- 后端保留现有 `days` 查询兼容性，并增加可选 `start_date`、`end_date` 参数；当日期范围参数存在时按明确范围查询。
- 查询仍按 `event_time` 优先、`created_at` 兜底；范围使用明确的 Asia/Shanghai 日期边界转换为带时区时间。
- 日历支持点击未来日期、上一天/下一天和回到今天。
- 增加 `schedule` 与 `reminder` 的展示标签和筛选能力。

### 3. 日程与提醒落库

- 复用现有 `record_event` 链路和 `life_events` 表，不新增通知 worker。
- 在 Agent 输出与 SQL 写入之间增加时间标准化边界，支持：
  - 今天、明天、后天；
  - 上午、下午、晚上；
  - 中文小时表达和 `HH:MM`；
  - 提前半小时、提前 N 分钟。
- 例句“明天下午三点有组会，提醒我提前半小时准备汇报材料”保存为两条事件：

  1. `2026-08-28 15:00 Asia/Shanghai`，`event_type=schedule`，内容为组会；
  2. `2026-08-28 14:30 Asia/Shanghai`，`event_type=reminder`，内容为准备汇报材料。

- 原始输入保留在 `source_text`；无法安全解析的时间不猜测，保留原文并返回明确的补充提示。
- 增加单元测试覆盖时间解析、跨日提醒、无时间输入和非法时间。

## 数据流

```text
聊天输入
  -> Intent/生活事件抽取
  -> 相对时间标准化
  -> 生成 schedule/reminder 事件
  -> MemoryAgent/MemoryService 保存 life_events 与 memories
  -> Timeline 按 start_date/end_date 查询
  -> 未来日期显示事件
```

## 错误处理

- 时间解析失败不伪造绝对时间；事件仍可保存为无时间记录，回复中提示用户补充日期或时间。
- 数据库不可用时保持现有 `AGENT_PROCESSING_ERROR` 行为，不返回“已保存”成功文案。
- 日期范围非法返回现有统一错误格式。
- seed 只允许操作带有明确演示标记的记录。

## 验收标准

1. 刷新聊天页或时间轴页不会新增数据库记录。
2. 重复运行演示 seed 不会产生重复批次。
3. 日历可以选择并浏览明天及未来 30 天。
4. 发送示例日程后，API 返回至少两条抽取事件，数据库保存 15:00 主事件和 14:30 提醒事件。
5. 选择明天日期时，前端显示组会和准备汇报材料两条记录。
6. 现有后端回归测试、前端契约测试和生产 E2E 继续通过。
