# 成员二、成员三代码冲突解决复盘与集成手册

日期：2026-08-25  
项目：LifeSteward  
适用范围：多人并行开发中，数据库/Tool 基线与 Agent 编排增量发生重叠时的集成工作

---

## 一、事件背景与最终结论

### 1.1 背景

成员二负责 PostgreSQL、pgvector、migration、`SQLTool`、`VectorSearchTool` 和数据库真实联调；成员三负责 Memory/Reflection/Planning Agent、生产依赖注入、Prompt 和 Agent 测试。

成员二的 Day4 成果已经进入 `main`，成员三的成果位于 `feature_day3_memory_reflection`。成员三的分支基于较早提交继续开发，而此期间 `main` 已经吸收了成员二的新实现。双方因此在同一批后端文件上形成了不同版本。

直接合并成员三原始分支时，Git 在以下位置报告了冲突：

- `backend/agents/master_agent.py`
- `backend/core/settings.py`
- `backend/main.py`
- `backend/migrations/001_initial_memory_schema.sql`
- `backend/requirements.txt`
- `backend/services/memory_service.py`
- 多个 Tool、测试文件和大量 `__pycache__/*.pyc`

这说明冲突并非单一文件问题，而是基线、职责边界、生成文件和生产编排同时发生了分叉。

### 1.2 最终采用的集成原则

> 成员二的代码作为数据库与 Tool 层基线，成员三的代码作为 Agent 生产编排和 Planning/Reflection 增量；不允许任何一方整目录覆盖另一方。

该原则决定了每类文件的处理方式：

| 代码领域 | 权威基线 | 集成策略 |
|---|---|---|
| PostgreSQL、pgvector、migration | 成员二 / `main` | 保留基线，不采用成员三旧副本覆盖 |
| `SQLTool`、`VectorSearchTool` | 成员二 / `main` | 保留接口和实现，只验证 Agent 调用是否兼容 |
| Memory/Reflection/Planning Agent | 成员三 | 以增量方式接入现有生产链路 |
| `MasterAgent` 路由 | 双方交界区 | 基于 `main` 手工加入 Planning/Reflection 编排 |
| Composition Root、生产依赖注入 | 成员三职责，依赖成员二基础设施 | 保留真实 Tool/Database 对象，增加生产 wiring 验证 |
| Prompt | 成员三 | 只加入有明确行为价值的规则，并用测试锁定 |
| requirements、settings | 共享区域 | 合并有效配置，保留版本上限和明确环境加载路径 |
| 缓存、备份、重复文件 | 无 | 排除，不进入集成结果 |

### 1.3 最终结果

- 创建隔离集成分支：`codex/integrate-memory-reflection`
- 形成 8 个小而独立的集成提交
- 修改 15 个文件，新增 343 行，删除 45 行
- 最终测试结果：`Ran 79 tests`，`OK (skipped=7)`
- 7 项跳过均因未配置 `POSTGRES_DSN` 或 `REDIS_URL`，不是代码失败
- PR #4 已合并到 GitHub `main`
- 最终合并提交：`5b26a77`
- GitHub `main` 已包含集成功能；成员三原始分支没有被反向修改

需要特别说明：真实 PostgreSQL、pgvector 和 Redis 环境测试仍需在具备对应环境变量后执行。单元测试通过不能替代真实基础设施验收。

## 二、本次遇到的问题及根因

### 2.1 分支基线过旧

成员三分支与合并前 `main` 的共同基线为 `0739b13`。此后成员二和其他成员已经在 `main` 中推进数据库、Tool、测试、前端和项目规范，成员三又在旧基线上修改了相同后端区域。

根因不是“Git 不会合并”，而是两个分支分别形成了新的事实来源。只依靠自动合并无法判断哪个数据库实现、哪个 migration 或哪个依赖版本才是当前正确版本。

经验：功能分支存活越久，越需要定期同步 `main`；等待到功能全部完成再合并，冲突数量和语义风险都会快速增加。

### 2.2 职责边界存在，但没有落实到文件所有权

任务文档已经约定成员二负责数据库/Tool，成员三负责 Agent/Service，但成员三分支仍包含 `database.py`、`sql_tool.py`、`vector_search_tool.py`、migration 和数据库测试等副本。

这导致 Git 看到的是“双方都修改同一文件”，而团队真正想表达的是“成员二拥有底层实现，成员三只依赖冻结接口”。

经验：口头或任务文档中的职责划分不够，必须进一步落实为目录或文件级所有权，并明确跨边界修改需要双方确认。

### 2.3 直接合并会把正确功能和过期副本绑在一起

成员三分支同时包含有价值的 Agent 增量和不应覆盖 `main` 的底层副本。如果直接接受整个分支，会把以下内容一并带入：

- Planning/Reflection 和生产编排等有效功能
- 旧版数据库与 Tool 实现
- 重复 migration、测试和规范文件
- 备份目录 `sync_backup_*`
- 手工验收脚本和过期副本
- 已生成的 Python 缓存文件

经验：一个分支并不天然等于一个可整体接受的变更集。发生跨职责开发后，应按“能力”而不是按“目录”进行集成。

### 2.4 生成文件制造大量无意义冲突

成员三分支提交了多个 `__pycache__/*.pyc`。`main` 已通过 `.gitignore` 清理这些文件，因此合并时出现大量 `modify/delete` 冲突。

这些二进制缓存既无法人工审查，也不应成为产品源码的一部分，却显著增加了冲突噪声，掩盖真正需要判断的业务文件。

经验：缓存、编译产物、虚拟环境、`.env`、日志和备份目录必须在首次提交前排除。清理生成文件是降低冲突成本最有效的措施之一。

### 2.5 同名文件冲突背后是语义冲突

以下冲突不能用“保留 ours”或“保留 theirs”简单处理：

- `master_agent.py`：成员二基线包含现有生产流程，成员三增加 Planning/Reflection 路由。
- `main.py`：涉及应用启动、依赖生命周期和真实 MemoryService 注入。
- `memory_service.py`：涉及 Agent 调用契约与 Tool 实现之间的边界。
- migration：双方文件同名，但数据库 schema 的权威来源只能有一个。
- `requirements.txt`：成员三需要运行服务器依赖，但其 OpenAI 版本缺少主版本上限。
- `settings.py`：需要支持 `.env`，同时避免依赖当前工作目录或产生不可控导入副作用。

经验：文本冲突只是表面，真正要解决的是运行时职责、接口契约、数据所有权和兼容性。

### 2.6 生产代码与测试代码可能使用不同依赖

成员三的 Agent 单元测试可以通过 Fake/Mock，但正式 `/api/v1/chat` 曾默认创建使用 `InMemoryMemoryService` 的 `MasterAgent`。这意味着“组件存在”和“生产链路实际使用组件”是两件事。

经验：必须测试 composition root 或生产 wiring，验证正式入口注入的确实是 `ToolMemoryService`、共享数据库客户端和真实 Tool，而不能只测试孤立 Agent。

### 2.7 Prompt 冲突属于功能缺陷，不是文案问题

集成中发现三类风险：

- 事实型记忆查询可能被错误分类为 reflection。
- 无检索结果时，交互层可能编造用户历史或声称保存了不存在的事件。
- 生活事件抽取可能补全用户未提供的时间、地点或细节。

经验：Prompt 是生产逻辑的一部分。关键安全规则必须有自动化测试，不能只靠人工阅读和主观判断。

### 2.8 环境配置依赖当前目录

测试需要从 `backend` 目录运行，否则可能出现模块导入错误；`.env` 如果仅按当前工作目录加载，也会在不同启动位置表现不一致。

最终将环境文件定位为相对于 `backend/core/settings.py` 的固定路径，并使用不覆盖已有系统环境变量的加载策略。

经验：配置文件路径应相对于代码或项目根确定，不能依赖开发者恰好从哪个目录启动程序。

### 2.9 依赖文件既要补齐，也要保留兼容边界

最终需要增加 `uvicorn>=0.30.0`，但不能直接复制成员三完整 requirements，因为这样会把 `openai>=1.66.0,<2` 变成无主版本上限的依赖。

经验：依赖冲突应逐项合并。新增缺失运行依赖，同时保留已验证的版本约束；禁止用整文件覆盖解决依赖差异。

### 2.10 Git 操作目录和顺序造成误判

实际操作中出现过以下问题：

- 已经位于 `backend`，却再次使用 `backend/requirements.txt`，实际指向不存在的 `backend/backend/requirements.txt`。
- `git add` 失败后继续执行 `git commit`，因此没有内容可提交。
- 未产生新提交就执行 `git push`，Git 显示 `Everything up-to-date`。
- GitHub 已经合并，但本地旧 `main` 没有拉取，导致误以为远端也未合并。
- GitHub 显示 `Delete branch` 被误解为尚未合并；实际上它只是提示源分支可以删除。

经验：每一步都要阅读命令输出。暂存、提交、推送、远端合并和本地同步是五个不同状态，不能互相替代。

### 2.11 本地 `main` 有未提交修改，不能直接同步

原始工作区的 `main` 落后远端，同时包含多项未提交的前端修改。此时直接拉取或合并可能把本次后端集成问题与前端在制工作混在一起。

最终选择通过 GitHub PR 完成远端合并，并暂不更新原始工作区。

经验：发现目标工作区不干净时，应停止本地合并，先保护已有工作；隔离工作区和远端 PR 是更安全的路径。

## 三、实际解决方式与关键决策

### 3.1 先建立隔离工作区

使用独立工作区 `D:\桌面\黑客松项目开发-集成` 和分支 `codex/integrate-memory-reflection` 完成集成。

这样做带来三个直接收益：

1. 不触碰原始工作区中未提交的前端代码。
2. 可以始终以最新 `main` 为基线检查成员三增量。
3. 每一步都可以独立测试、提交和回退。

### 3.2 不执行成员三原始分支的整分支合并

原始分支包含大量跨边界文件和生成产物，模拟合并已经确认会产生内容冲突、add/add 冲突和 modify/delete 冲突。

因此没有尝试逐个消除所有冲突标记后整体提交，而是从 `main` 出发，把成员三有价值的功能按行为重新接入。这避免了“为了解掉冲突而接受错误版本”。

### 3.3 保留成员二数据库与 Tool 基线

以下部分没有被成员三目录覆盖：

- 数据库连接和 schema 事实来源
- `SQLTool` 和 `VectorSearchTool` 的当前实现
- PostgreSQL/pgvector migration
- 数据库测试与版本约束

成员三 Agent 通过冻结接口使用这些能力，保持 `API -> Service -> Agent -> Tool -> Database` 分层。

### 3.4 分八个小提交引入 Agent 增量

最终集成提交如下：

| 提交 | 目的 |
|---|---|
| `5c69605` | 将 PlanningAgent 接入 MasterAgent，形成 `MemoryAgent -> PlanningAgent -> InteractionAgent` |
| `134c75b` | 区分事实记忆查询与 reflection |
| `bec5949` | 禁止交互层编造记忆或虚构保存结果 |
| `63282da` | 禁止事件抽取补全未知细节 |
| `e67c6f2` | 验证生产组合根使用真实 ToolMemoryService 和共享数据库客户端 |
| `d574fe1` | 覆盖 PlanningAgent 正常、非法 JSON、空计划和 LLM 异常边界 |
| `45fb2e9` | 明确从 `backend/.env` 加载配置，并补充示例配置 |
| `f32a3ca` | 增加 Uvicorn 运行依赖，同时保留 OpenAI 主版本上限 |

小提交使每次变更都只有一个目的，便于测试、审查和定位回归。

### 3.5 用测试保护语义合并

新增或强化的测试覆盖：

- Planning 路由顺序
- Prompt 意图分类和防幻觉约束
- 生产依赖注入
- PlanningAgent 降级行为
- `.env` 加载位置与配置示例
- Uvicorn 和 OpenAI 依赖边界

测试总数从成员二交接时的 67 项逐步增加到 79 项。最终结果为 72 项执行通过、7 项按环境条件跳过。

### 3.6 在 PR 前验证远端合并关系

在创建 PR 前完成了三类确认：

- 集成分支已经推送，工作区没有遗漏提交。
- 最新 `origin/main` 没有集成分支尚未包含的新提交。
- 模拟合并返回成功，不存在 Git 冲突。

GitHub 页面随后显示 `Able to merge`，PR #4 使用 merge commit 合入 `main`。

合并后再次确认：

- `origin/main` 指向合并提交 `5b26a77`。
- 最后一个功能提交 `f32a3ca` 是 `origin/main` 的祖先。
- 合并后 `origin/main` 的代码树与已测试的集成分支代码树完全一致。
- 完整测试再次通过。

## 四、下次可直接复用的标准流程

### 阶段 A：冻结现场

1. 暂停对冲突区域继续追加功能。
2. 明确源分支、目标分支、共同基线和最新远端状态。
3. 检查工作区是否存在未提交文件，不在脏工作区直接合并。
4. 记录当前可通过的测试和真实环境缺口。

产出：一份明确的“当前事实”，避免边解决边变化。

### 阶段 B：建立责任矩阵

对每个冲突模块回答三个问题：

1. 谁是该模块的负责人？
2. 哪个分支包含最新、已验证的基线？
3. 另一分支提供的是替代实现，还是应叠加的能力？

如果无法回答，先由负责人确认，不进入代码处理。

### 阶段 C：给冲突文件分类

| 分类 | 处理原则 |
|---|---|
| 权威基线文件 | 保留负责人版本 |
| 功能增量文件 | 迁移必要行为，不整文件覆盖 |
| 双方共同演进文件 | 依据接口、调用链和测试进行语义合并 |
| 生成文件 | 删除并加入忽略规则 |
| 备份、重复目录 | 不进入产品分支 |
| 不确定文件 | 暂停，查调用方、规范和测试后再决定 |

### 阶段 D：在隔离环境中集成

1. 从最新目标分支建立隔离分支和独立工作区。
2. 先确认基线测试，再开始修改。
3. 一次只引入一个行为，例如先接 Planning 路由，再处理 Prompt，再处理配置。
4. 每个行为配一组最小但有效的回归测试。
5. 每一步形成独立提交，禁止把清理、重构和功能混为一个提交。

### 阶段 E：验证真实调用链

不要只检查文件是否存在，应验证生产入口实际经过：

```text
API
-> Service
-> MasterAgent
-> Memory / Planning / Reflection Agent
-> ToolMemoryService
-> SQLTool / VectorSearchTool
-> PostgreSQL / pgvector
```

重点检查：

- 生产入口有没有仍然使用 Fake 或 InMemory 实现。
- Agent 是否只通过 `AgentState` 通信。
- Tool 是否保持冻结接口。
- 无数据、非法 LLM 响应和基础设施异常是否可以安全降级。
- Prompt 是否会虚构事实。

### 阶段 F：合并前质量门

只有同时满足以下条件才创建 PR：

- 所有预期文件已经提交并推送。
- 工作区没有意外修改和未跟踪产物。
- 完整测试通过，跳过项有明确原因。
- 依赖和配置可以从干净环境重建。
- 与最新目标分支的模拟合并无冲突。
- PR 描述明确说明保留了谁的基线、引入了谁的增量。

### 阶段 G：合并后验证

1. 确认 PR 状态为 merged，而不是仅 closed。
2. 确认目标分支包含最后一个功能提交。
3. 对合并后的代码树重新执行完整测试。
4. 暂不急于删除源分支和隔离工作区，先完成远端与本地状态确认。
5. 本地 `main` 若有未提交工作，先保护这些工作，再同步远端。

## 五、团队协作规则与验收清单

### 5.1 推荐责任矩阵

| 区域 | 主负责人 | 其他成员允许做什么 |
|---|---|---|
| Database、migration | 数据库负责人 | 通过已冻结接口调用；修改前必须确认 |
| Tool | Tool/数据库负责人 | 增加调用测试，不复制另一套实现 |
| Agent 编排 | Agent 负责人 | 使用 Tool 接口，不直接访问数据库 |
| Prompt | Agent 负责人 | 产品/测试共同审查关键行为 |
| API Schema、AgentState | 架构或接口负责人 | 变更需同步所有调用方和规范 |
| Composition Root | 后端集成负责人 | 负责把各层真实实现接入生产入口 |
| requirements、settings | 后端集成负责人 | 逐项合并并验证，不整文件覆盖 |

### 5.2 每日开发规则

- 每天开始开发前同步最新 `main`。
- 功能分支只携带本任务相关文件。
- 禁止提交 `__pycache__`、`.pyc`、`.env`、虚拟环境、备份目录和构建产物。
- 不使用“上传整个目录”代替正常 Git 增量提交。
- 跨职责修改必须在 handoff 或 PR 中写明原因。
- 一个提交只表达一个目的，提交信息描述行为而不是日期。
- 新增接口时同步更新协议、实现、调用方和测试。
- Agent 功能必须验证生产 wiring，不能只依赖 Mock 测试。
- Prompt 的分类和防幻觉规则必须有回归测试。

### 5.3 Handoff 最低要求

每次交接至少记录：

- 分支名称和最后提交号
- 修改文件及其影响范围
- 新增、修改或废弃的接口
- 完整测试结果
- 跳过测试及其环境原因
- 仍未完成的真实联调
- 与其他成员职责的交界点
- 下一位成员可以依赖的冻结事实

“代码已经完成”不是有效交接；必须说明生产入口是否真的使用了该代码。

### 5.4 冲突处理检查表

#### 开始前

- [ ] 已获取最新远端状态
- [ ] 已确认源分支和目标分支方向
- [ ] 已确认目标工作区干净，或已建立隔离工作区
- [ ] 已找到共同基线
- [ ] 已建立模块责任矩阵
- [ ] 已记录当前测试基线

#### 处理中

- [ ] 没有整目录覆盖
- [ ] 没有使用单纯 ours/theirs 代替语义判断
- [ ] 数据库和 Tool 使用权威基线
- [ ] Agent 增量按行为接入
- [ ] 生成文件和备份目录已排除
- [ ] 每个行为都有对应验证
- [ ] 每个提交只解决一个问题

#### 合并前

- [ ] 完整测试通过
- [ ] 跳过项有书面解释
- [ ] 生产依赖注入已验证
- [ ] Prompt 关键规则已测试
- [ ] requirements 和环境配置已检查
- [ ] 与最新 `main` 无冲突
- [ ] 所有本地提交已经推送

#### 合并后

- [ ] PR 明确显示 merged
- [ ] 目标分支包含最后功能提交
- [ ] 合并结果再次通过测试
- [ ] 没有误删仍需保留的源分支或工作区
- [ ] 本地旧 `main` 在保护未提交工作后再同步
- [ ] 团队成员已获知新的权威基线

### 5.5 冲突决策口诀

> 先定所有权，再看调用链；先保基线，再加增量；生成物删除，重复物排除；一次一行为，测试后提交；远端已合并，不等于本地已同步。

---

## 六、本次复盘的核心经验

1. **冲突数量多通常不是 Git 技术问题，而是职责和基线管理问题。**
2. **不要把“解决冲突标记”误认为“完成正确集成”。** 文件可以无标记但运行逻辑仍然错误。
3. **数据库与 Agent 并行开发必须依赖冻结接口，而不是互相复制实现。**
4. **整分支合并不是默认正确选项。** 当分支包含跨职责旧副本时，基于最新 `main` 重放有效增量更安全。
5. **生产 wiring 是 Agent 系统最容易遗漏的环节。** 单元测试中的 Agent 可用，不代表正式 API 已使用它。
6. **Prompt、配置和依赖都是功能代码。** 它们需要测试、版本边界和审查。
7. **Git 状态必须分层理解。** 暂存、提交、推送、PR 合并和本地同步分别验证。
8. **隔离工作区保护了已有工作，也让集成过程可回退。** 发现本地 `main` 不干净时，不应硬拉取。
9. **测试通过要准确表述。** 本次是 79 项被发现，其中 72 项执行通过、7 项按环境跳过；真实数据库验收仍需补做。
10. **最好的冲突解决发生在写代码之前。** 明确所有权、保持短分支、频繁同步和小提交，比事后处理几十个冲突更便宜。

本次成功的关键不是选择了某一方的全部代码，而是建立了清晰的权威基线，并把另一方真正有价值的能力以可验证的增量接入。
